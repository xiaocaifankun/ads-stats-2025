# Agent 记忆系统Agent Memory System

大语言模型**天生无状态**——每次调用都从零开始。记忆系统是把无状态的模型变成「记得你、记得项目、记得经验」的系统的那层基础设施：一部分活在上下文窗口里，一部分存在窗口之外的文件与数据库中。
LLM 无状态 → 记忆是给 Agent 的「连续性」 记忆按「存哪」×「存多久」分型：工作 / 语义 / 情景 / 程序 落地有快慢两个回路：Record 写入 & Retrieve 读取
PART A · 通用原理
### 通用 Agent 记忆系统

这一部分讲所有 Agent 框架共享的记忆本质：为什么要记忆、记忆分几种、读写回路怎么跑、有哪些铁律。它不绑定任何具体产品。
01
## 它是什么

**「无状态」是问题，「记忆」是解：让信息能跨一次推理、跨一个会话、甚至跨多个会话存活。**记忆不在模型里，而在系统给它搭的「能存能取」的容器里。

<!-- 图 -->

```text
无状态模型 · 每次都从零开始
裸 LLM
回答完即忘 · 无任何保留
下一次调用
连接断掉 · 信息不跨调用
带记忆的系统 · 连续性由此而来
Agent + 记忆层
上下文里推理 · 记忆里存取
记忆存储
文件 · 数据库 · 向量库
读取   写入
跨会话也记得 · 信息可回取
```

> 记忆的本质：在「裸模型」外加一层可存取的容器。左为无状态、每次断连；右为接入记忆层后形成读写回路。

## 核心设计

**记忆按两条轴分类：存哪里（参数量/文本量）× 存多久（短期/长期）。**认知科学的分类法（工作、情景、语义、程序记忆）被工程界直接借用，作为架构清单。

```text

按类型 × 时长

情景记忆 Episodic
```

> 最简工作模型：工作记忆（上下文内，实时）＋ 语义 / 情景记忆（外部，持久）。判据是信息是否需要跨会话存活。

## 运行全程

**记忆系统靠一对读写回路运转：推理前 Retrieve（从长期记忆捞回注入上下文），推理后 Record（把短期对话提炼存入长期记忆）。**上下文窗口装不下时，还要靠上下文工程来压缩。

<!-- 图 -->

```text
用户   工作记忆 · 上下文窗口   长期记忆 · 外部存储
提问
当前上下文
会话历史 · 系统提示
① 检索 Retrieve · 拉回相关记忆
长期记忆
用户画像 · 经验 · 事件
向量库 · 图库 · 文件
② 注入 ③ 推理作答
模型推理
结合注入的记忆生成
得到回答
④ 巩固 Consolidate · 提炼并写入
写入常在会话结束或触发点批量执行
```

> 读写回路：Retrieve（①→②→③）让长期记忆参与当下推理；Record（④）把当下的有效信息沉淀回长期记忆。两端循环即「会记得的 Agent」。
**上下文窗口是稀缺资源，装不下时要压缩。**Anthropic 给出三条不写坏上下文的路径。


> 上下文工程三策略（Anthropic）：压缩保连续性、笔记提供持久、子代理隔离重活。按任务类型选，而非全用。
04
## 铁律

- **先问「这条信息要不要跨会话活」，再决定放哪。** 只在当前推理用的放工作记忆；要活到下次会话的才放进外部长期记忆。放错层是记忆设计最常见的失误。_记忆分类学 · Mastra/Teachahead 2026_
- **上下文窗口是稀缺资源，不是无限缓冲。** 工作记忆里每个 token 都是挤占推理的 token。Anthropic 直言核心是把上下文当作有限资源来经营。_Anthropic 2026_
- **写入要提炼，读取要按相关性筛——不要照搬原始记录。** Record 不是存原始对话，而是 LLM 抽取「事实/偏好/经验」；Retrieve 不是全量回放，而是按 query 检索 top-k。巩固太激进存噪音，太保守丢信息。_记忆系统工程 · Mem0 类方案_
- **长期记忆要分清读取范围，防止跨项目串味。** 语义记忆按用户、项目、工具分域：存进工作区级别的记忆不该泄漏到别的项目；检索时也要带上 scope 约束。_Anthropic Managed Agents · 2026_
- **持久记忆要防「陈腐」与「冲突」。** 存下的事实会过期（陈腐）、两次写入会矛盾（冲突）。没有显式的刷新/冲突规则，旧的错记忆会挤掉新的对信息——即上下文污染。_persistent-memory 设计问题 · 2026_

## WorkBuddy 的三层记忆

**WorkBuddy 把通用模型的记忆落成三层，作用域从最宽到最窄：云端记忆（跨所有项目自动）→ 用户级本地（跨项目显式）→ 项目级工作区（单项目）。**三层并存的判据正是 Part A 的铁律一——按信息该活多久、活多广来决定落哪层。

```text

L1 · 云端记忆
Cloud Memory
只读 · 自动注入

另有历史对话检索，可回查很久以前的讨论
L2 · 用户级本地

```

> WorkBuddy 三层记忆：L1 云端自动画像（最宽、只读）、L2 用户级显式（跨项目）、L3 项目级（单项目）。自上而下由自动到显式、由宽到窄。
**读写时机各不同，正好对应通用模型的两条回路。**下面把每一层的「谁写、何时读、存哪」摊开成表。

| 层级 | 写入方 | 读取时机 | 路径 |
|---|---|---|---|
| L1 云端 | 服务端自动（不可控） | 每次会话开场注入 | `~/.workbuddy/memory/…_memory.md` |
| L2 用户级 | 我主动请求「长期记住」 | 需要非项目规则时回查 | `~/.workbuddy/MEMORY.md` |
| L3 项目级 | 完成任务后我追加（日志只增） | 同项目恢复上下文时回查 | `.workbuddy/memory/MEMORY.md` + `YYYY-MM-DD.md` |

### 第 1 题（基础 · 识别 · 通用）

为什么「裸的大语言模型」需要外加一套记忆系统？
- A. 因为模型的知识会随训练而遗忘
- B. 因为模型天然无状态，每次调用都从零开始，无法记住上次对话 ✅
- C. 因为模型的参数量不足以存下所有信息
- D. 因为模型只能理解提示词，无法进行推理

**解析**：LLM 是无状态的：每次 API 调用都独立。记忆系统正是为了把信息跨一次推理、跨会话地保留与回取，把无状态模型变成有连续性的系统。

*对应章节：`sec-01`*

### 第 2 题（基础 · 识别 · 通用）

「用户偏好 Python 而非 JavaScript」这类与具体时间无关的知识，属于哪类记忆？
- A. 情景记忆 Episodic
- B. 工作记忆 Working
- C. 语义记忆 Semantic ✅
- D. 程序记忆 Procedural

**解析**：语义记忆存与时间解耦的事实、偏好、领域知识——像一本「关于用户/主题的百科」。情景记忆则记录「某时某刻发生了什么」。

*对应章节：`sec-02`*

### 第 3 题（进阶 · 理解 · 通用）

记忆读写回路中，Retrieve（读取）这一步发生在什么时候、起什么作用？
- A. 在会话结束时，把整段对话原样存档
- B. 在推理前，从长期记忆检索相关条目注入当前上下文 ✅
- C. 在模型训练时，把记忆写入权重
- D. 在输出后，对回答做自动纠错

**解析**：Retrieve 发生在推理前：把长期记忆里与当前 query 相关的信息捞回、注入工作记忆，辅助这次作答。写入长期记忆的步骤是 Record / Consolidate，发生在推理后。

*对应章节：`sec-03`*

### 第 4 题（进阶 · 理解 · WorkBuddy）

WorkBuddy 三层记忆中，哪一层是「会话开始时由服务端自动注入、我只读不可改写」的？
- A. L1 云端记忆（长期用户画像） ✅
- B. L2 用户级本地 MEMORY.md
- C. L3 项目级 .workbuddy/memory
- D. 以上三者都是用户显式写入

**解析**：L1 云端记忆由服务端基于历史自动生成的 profile 在每次会话开场注入，是只读的、自动的。L2/L3 才是显式或半自动写入的本地文件。

*对应章节：`sec-05`*

### 第 5 题（挑战 · 应用 · WorkBuddy）

你有一条项目专属的约定（如「本仓库用 speckit 工作流」），想让同项目后续会话都知道，但不要污染其它项目。应写入哪一层？
- A. 用户级 ~/.workbuddy/MEMORY.md
- B. 项目级 .workbuddy/memory/MEMORY.md ✅
- C. 云端记忆（它会自动学习）
- D. 不要记，每次手动说明

**解析**：这是项目级约定：落 L3 项目级 MEMORY.md 最合适——只在当前项目恢复上下文时回查，避免把项目专属规则泄漏到全局。铁律四强调记忆要分清 scope。

*对应章节：`sec-05`*

### 第 6 题（挑战 · 应用 · 通用）

一个 agent 在长任务中上下文即将爆满。按 Anthropic 的建议，最适合优先采取的措施是？
- A. 什么都不做，让模型自己处理长上下文
- B. 对接近上限的历史做压缩摘要，用摘要重启窗口 ✅
- C. 把所有工具结果永远保留在上下文里以防遗漏
- D. 换成上下文窗口更大的模型即可一劳永逸

**解析**：上下文是有限资源。Compaction 把接近上限的对话压缩成高保真摘要（保留架构决策、未决问题）再续跑，是最直接的长期连贯手段。只换大窗口不解决上下文污染问题。

*对应章节：`sec-03`*
