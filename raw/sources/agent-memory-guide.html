Agent 记忆系统Agent Memory System

大语言模型天生无状态——每次调用都从零开始。记忆系统是把无状态的模型变成「记得你、记得项目、记得经验」的系统的那层基础设施：一部分活在上下文窗口里，一部分存在窗口之外的文件与数据库中。

LLM 无状态 → 记忆是给 Agent 的「连续性」 记忆按「存哪」×「存多久」分型：工作 / 语义 / 情景 / 程序 落地有快慢两个回路：Record 写入 & Retrieve 读取
PART A · 通用原理

通用 Agent 记忆系统

这一部分讲所有 Agent 框架共享的记忆本质：为什么要记忆、记忆分几种、读写回路怎么跑、有哪些铁律。它不绑定任何具体产品。

01

它是什么

「无状态」是问题，「记忆」是解：让信息能跨一次推理、跨一个会话、甚至跨多个会话存活。记忆不在模型里，而在系统给它搭的「能存能取」的容器里。

02

核心设计

记忆按两条轴分类：存哪里（参数量/文本量）× 存多久（短期/长期）。认知科学的分类法（工作、情景、语义、程序记忆）被工程界直接借用，作为架构清单。

03

运行全程

记忆系统靠一对读写回路运转：推理前 Retrieve（从长期记忆捞回注入上下文），推理后 Record（把短期对话提炼存入长期记忆）。上下文窗口装不下时，还要靠上下文工程来压缩。

上下文窗口是稀缺资源，装不下时要压缩。Anthropic 给出三条不写坏上下文的路径。

04

铁律

  1. 先问「这条信息要不要跨会话活」，再决定放哪。 只在当前推理用的放工作记忆；要活到下次会话的才放进外部长期记忆。放错层是记忆设计最常见的失误。记忆分类学 · Mastra/Teachahead 2026
  2. 上下文窗口是稀缺资源，不是无限缓冲。 工作记忆里每个 token 都是挤占推理的 token。Anthropic 直言核心是把上下文当作有限资源来经营。Anthropic 2026
  3. 写入要提炼，读取要按相关性筛——不要照搬原始记录。 Record 不是存原始对话，而是 LLM 抽取「事实/偏好/经验」；Retrieve 不是全量回放，而是按 query 检索 top-k。巩固太激进存噪音，太保守丢信息。记忆系统工程 · Mem0 类方案
  4. 长期记忆要分清读取范围，防止跨项目串味。 语义记忆按用户、项目、工具分域：存进工作区级别的记忆不该泄漏到别的项目；检索时也要带上 scope 约束。Anthropic Managed Agents · 2026
  5. 持久记忆要防「陈腐」与「冲突」。 存下的事实会过期（陈腐）、两次写入会矛盾（冲突）。没有显式的刷新/冲突规则，旧的错记忆会挤掉新的对信息——即上下文污染。persistent-memory 设计问题 · 2026
PART B · 具体落地

WorkBuddy 的记忆设计

现在把 Part A 的通用模型放到一个真实产品里看：WorkBuddy 如何在「云端自动画像、用户级跨项目、项目级当日」三个层上落地记忆。所有路径与行为都以本机实测文件为准。

05

WorkBuddy 的三层记忆

WorkBuddy 把通用模型的记忆落成三层，作用域从最宽到最窄：云端记忆（跨所有项目自动）→ 用户级本地（跨项目显式）→ 项目级工作区（单项目）。三层并存的判据正是 Part A 的铁律一——按信息该活多久、活多广来决定落哪层。

读写时机各不同，正好对应通用模型的两条回路。下面把每一层的「谁写、何时读、存哪」摊开成表。

层级 写入方 读取时机 路径
L1 云端 服务端自动（不可控） 每次会话开场注入 ~/.workbuddy/memory/…_memory.md
L2 用户级 我主动请求「长期记住」 需要非项目规则时回查 ~/.workbuddy/MEMORY.md
L3 项目级 完成任务后我追加（日志只增） 同项目恢复上下文时回查 .workbuddy/memory/MEMORY.md + YYYY-MM-DD.md
