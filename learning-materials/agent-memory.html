概念学习卡片 / Concept Learning Card

Agent 记忆系统 Agent Memory System — 为什么 Agent 需要「记忆」，以及它到底记什么、怎么记

一句话定义：Agent 记忆系统是让 AI Agent
在单次对话之外保留、检索并更新信息的机制——
它把「无状态的模型调用」补齐成「有历史、有经验、有个性的持续体」。

生成日期 2026-09-10 视角 从 AI Agent 工程实践出发 来源 12 条 · 全部已校验可访问

01学习目标

学完这份资料，你应该能够：

  1. 说清「记忆」在 Agent 里不是指模型参数。能够区分「模型权重里冻结的知识」和「运行时需要被管理、被检索、被更新的上下文信息」，并解释为什么后者才是工程问题。
  2. 按类型拆解一个 Agent 的记忆组成。能独立说清工作记忆、语义记忆、情景记忆、程序记忆各自「存什么、什么时候用、什么时候写」，并能举出一个具体 Agent 产品里对应到哪个部件。
  3. 判断什么场景该引入记忆、什么场景不该。能识别引入记忆带来的风险（过期信息污染、上下文膨胀、幻觉加固），并给出至少两条边界判据。

02核心问题

围绕「Agent 记忆系统」，最值得先搞清楚的是这四个问题：

  1. 模型本身没有记忆，为什么 Agent 却需要记忆？——从「一次 stateless 的前向计算」到「跨会话的持续行为」，中间缺的那一块到底是什么。
  2. 记忆分几类，各自解决什么问题？——是简单的「存聊天记录」，还是不同类型的信息需要不同的写入、检索与淘汰策略？
  3. 上下文窗口越来越长，记忆还需要吗？——如果上下文能装 100 万 token，为什么工程上还要做压缩、摘要、外置存储？
  4. 记忆什么时候会变成负债？——什么信息一旦被写进去，反而会让 Agent 表现更差。

03个人解释（第一人称）

说明：以下为本人的理解表述，用于自我复核；欢迎直接在原文上批注修改。

我理解 Agent 记忆系统，本质上不是一个「数据库功能」，而是一个上下文供给问题。模型每次被调用时都是无状态的——它这次能"看见"什么，完全取决于我们这次往 prompt 里塞了什么。所以所谓"记忆"，其实就是决定这一次该把哪些过往信息重新递到模型面前。

一开始我以为"记忆"就是把聊天历史全带上。后来发现这个思路很快就撞墙：对话一长，上下文塞满，模型反而答得更差；而且"聊天记录"和"我知道用户是素食主义者"根本不是一类信息——前者是流水，后者是结论。所以真正的记忆系统必须做两件事：一是把流水压缩成结论（写入/整合），二是需要的时候把对的结论捞回来（检索）。这也是为什么几乎所有实现最终都会落成"存储 + 检索 + 更新"三段式。

它和 RAG 最大的不同是：RAG 检索的是外部知识库，内容相对静态、与"我"无关；而记忆检索的是关于这段交互关系本身的信息——用户是谁、上次做到哪、哪些做法失败过。可以说 RAG 是"查资料"，记忆是"记事"。

还有一个让我改变认知的点：记忆不是越多越好。[来源 12] 一份针对长上下文的测试报告显示，把关键信息埋进更长的上下文里，模型找到它的能力会非均匀地下降——也就是说，存进去 ≠ 用得上。这让我意识到记忆系统的核心 KPI 不是"存了多少"，而是"召回准不准、信噪比高不高"。

04核心机制 / 组成

4.1 四类记忆：分别存什么

目前被引用最广的分类框架是 CoALA（Cognitive Architectures for Language Agents）提出的模块化记忆划分：把一个 Agent 的记忆拆成工作记忆加三类长期记忆。[来源 1]

图 1 · 记忆类型分类：一块易失的工作台 + 三个可持久化的仓库
工作记忆Working Memory
存什么：当前这一步推理所需的全部材料——本轮对话、工具返回结果、刚检出来的记忆片段。
特点：易失、容量受上下文窗口硬约束，每次模型调用都要重新组装一次。
语义记忆Semantic
存什么：关于世界与用户的事实性知识——"用户在准备考研"、"团队用的是 PostgreSQL"。
特点：回答"什么是真的"，与具体某次经历解耦，可跨会话复用。
情景记忆Episodic
存什么：具体经历——"上次用 EMR 跑这个脚本超时了，后来改成并发跑通了"。
特点：带时间与情境，回答"下次该怎么做"，能保留失败教训。
程序记忆Procedural
存什么：规则与技能——系统提示里的行为准则、被固化下来的固定工作流。
特点：最稳定，通常直接写进 prompt 或代码，而非动态检索。
图说：工作记忆是"这轮对话正在用的工作台"，用完即清；语义/情景/程序记忆是三个可持久化的仓库，分别存事实、经历、规则。一个常见的类比是：工作记忆像操作系统的内存/寄存器，长期记忆像硬盘。"工作记忆易失"与"长期记忆可持久化"是这张对比图的核心。

4.2 三个动作：写入、检索、淘汰

无论哪家实现，记忆系统的运作都可以拆成三个动作，区别只在于"谁在什么时候触发"：

  • 写入（Write / Extraction）：判断新产生的信息值不值得记，并转成结构化条目。路径有两条——hook 自动采集（每轮都抓，优点是"不漏"，代价是噪声多）与 工具主动调用（模型自己决定要不要记，优点是"准"，风险是"漏"）。[来源 8]
  • 检索（Retrieve / Recall）：在当前任务下挑出最相关的若干条，塞进工作记忆。这是决定效果好坏的关键环节。
  • 淘汰与整合（Consolidate / Forget）：处理冲突与冗余——更新过期事实、合并相似条目、丢掉不再相关的记录。这一步最容易被忽略，但恰恰是"记忆不腐烂"的关键。

框架层的分工可以看 LangChain 的设计：短期记忆是 thread-scoped 的，由 checkpointer（如 MemorySaver、PostgresSaver）按会话线程持久化；长期记忆则用自定义 namespace 组织，通过 Store API（如 InMemoryStore、PostgresStore）以 namespace + key 的层级结构存 JSON。[来源 5] 另一个角度是写入时机：在"热路径"（对话中实时写）还是"后台任务"（异步批量写）执行，会直接影响延迟与召回质量——LangMem SDK 提供的 create_memory_manager 就是为了让这件事可配置。[来源 9]

4.2.1 存储形态不止一种

上述讨论都默认记忆存在"文本条目库"里，但并非唯一选择。MCP 官方的 memory server 就采用本地知识图谱方案：把信息拆成 Entities（实体）、Relations（关系，要求用主动语态表述）、Observations（关于实体的原子事实）三要素，提供 9 个工具（create_entities、create_relations、add_observations、delete_entities、delete_observations、delete_relations、read_graph、search_nodes、open_nodes），数据以 JSONL 形式落盘。[来源 10] 学术方向上也有从神经科学借鉴的探索，例如 HippoRAG 类比海马体的索引机制来组织长期记忆。[来源 11]

4.3 检索怎么算分：一个可解释的公式

最经典也最容易理解的检索打分来自 Stanford 的 Generative Agents 实验。它给每条记忆算一个总分，由三项加权相加：[来源 2]

score = α₁ · recency + α₂ · importance + α₃ · relevance　（论文中 α₁ = α₂ = α₃ = 1）
  • recency（新鲜度）：用指数衰减计算，形式为 0.99^Δt，其中 Δt 以小时为单位。也就是说记忆每多放一小时，新鲜度就乘 0.99。
  • importance（重要性）：让 LLM 对这条记忆打一个 1–10 分，判断它有多值得记住。
  • relevance（相关性）：当前查询与这条记忆的语义相似度。

在这个实验中，Agent 还被设计成会周期性"反思"：当累积的未处理记忆重要度超过阈值 150 时，触发一次 reflection，把零散观察抽象成更高层的结论写回记忆流。[来源 2]

4.4 当上下文装不下：分页与压缩

工作记忆受上下文窗口硬约束，于是出现了两类典型解法：

思路代表实现核心做法
虚拟内存分页 MemGPT [来源 3] 把上下文类比成操作系统虚拟内存：分成常驻的 main context 与容量近乎无限的 external context，由模型通过 function call 自行在两者间搬数据。
压缩与清空 Anthropic 上下文工程 [来源 4] 对话过长时做 compaction（把历史摘要成更短的表述）与 tool-result clearing（不再需要的工具返回结果清出上下文）；也可派生 sub-agent，只把 1000–2000 token 的压缩摘要交回主 Agent。
服务端自动压缩 Claude 平台 [来源 6] 在请求里配置 context_management，由服务端按策略自动压缩，客户端不必自己实现截断逻辑。
结构化笔记 Anthropic 上下文工程 [来源 4] 让 Agent 在上下文之外维护一份持久化的"笔记文件"，需要时再读回来（structured note-taking / agentic memory）。

4.5 工程上怎么落地：一个全托管实现的解剖

Amazon Bedrock AgentCore Memory 是一个把上面这些思路产品化的例子，可以直接当作"记忆系统标准件"来读：[来源 8]

  • 短期记忆：以不可变 event 的形式按 actorId + sessionId 存储，记录原始交互流水。
  • 长期记忆：由一条异步三阶段管道从短期记忆里提炼，见下图。
  • 三套策略 + 命名空间：semanticMemoryStrategy 存到 /facts/{actorId}/；userPreferenceMemoryStrategy 存到 /preferences/{actorId}/；episodicMemoryStrategy 存到 /reflect/{actorId}/。
  • 读写两条路径：用 hook 自动采集原始交互（追求"不漏"），或用 memory_store 工具让模型主动写入精选内容（追求"准"）。
图 3 · 长期记忆的异步三阶段管道（以 AgentCore Memory 为例）
STAGE 1Extraction 提取
从原始交互流水（短期记忆的 event 流）中抽取出值得长期保留的信息候选。
STAGE 2Consolidation 整合
候选信息与已有记忆做比对，做出三种决策之一：
ADD全新内容，直接新增一条记忆。
UPDATE与已有记忆冲突或可补充，改写原条目。
NO-OP已有记忆已覆盖，什么都不做。（避免重复堆积）
STAGE 3Reflection 反思
把零散的具体经历抽象成更高层的结论，写入 /reflect/{actorId}/。关键点是抽象层次要够高——例如把"某个具体工具超时"泛化成对某类环境（如 Serverless / 托管环境）的通用教训，这样结论才能跨场景复用。
图说：长期记忆不是"把短期记忆换个地方存"，而是经过三个异步阶段提炼：先提取候选信息，再整合（对已有记忆执行新增 / 更新 / 不动三种决策之一，防止冗余堆积），最后反思成更高层的抽象结论。图中标注的 ADD / UPDATE / NO-OP 三种整合决策，以及"反思要提升抽象层次"这一点，均来自 AgentCore Memory 的公开实践说明 [来源 8]。

05应用场景

一个具体的例子——面向客服团队的工单 Agent：

某 SaaS 公司的支持团队上线了一个 Agent，自动处理用户提交的技术工单。上线两个月后发现：虽然它单轮回答质量不错，但用户每次开新会话都得从头讲一遍背景，而且同一个坑它会在不同客户身上反复踩。于是团队补上记忆系统，具体分三处落地：

  1. 写偏好（语义记忆）：当会话里出现"我们线上跑在 Serverless 环境""我们不做每日备份"这类稳定事实时，由模型调工具写入 /preferences/{actorId}/。下次该客户再来，Agent 直接按这个前提给方案，不用再问一遍。
  2. 写教训（情景记忆）：当一次排查最终绕了弯路——比如某个诊断脚本在大数据量下超时——这条经历被写入情景记忆。下次遇到同类工单，Agent 优先推荐当时走通的那条路径。
  3. 跨场景泛化（反思）：把多起"超时"个案抽象成一条结论——"在这类托管环境下，先探数据规模再决定工具"，写入 /reflect/{actorId}/，使教训不再绑死在某个具体工具上。

这里的关键设计取舍来自公开实践总结：用 hook 自动采集保证"不漏"，用 memory_store 工具主动写保证"准"，两条路径并存。[来源 8]

06易混淆 / 使用边界

最容易搞混的三组概念

容易混关键区别
记忆 vs RAG RAG 检索外部知识库（文档、资料），内容与"我"无关；记忆检索关于交互关系本身的信息（用户偏好、历史经历）。一句话：RAG 查资料，记忆记事。
语义记忆 vs 情景记忆 语义记忆回答"什么是真的"（用户是素食者）；情景记忆回答"下次该怎么做"（上次这条路走不通）。情景记忆因为带情境，能保留失败教训并跨场景泛化，这是语义记忆做不到的。[来源 8]
短期记忆 vs 长期记忆 短期记忆是原始流水（不可变 event，按会话存）；长期记忆是提炼后的结论（由异步管道生成）。前者求全，后者求精。

什么时候"长上下文"替代不了记忆

一个常见误解是：既然上下文窗口已经到百万 token，直接全塞进去不就行了？针对长上下文的实测报告显示并非如此 [来源 12]：

  • 性能随长度非均匀衰减：上下文越长，模型对其中信息的注意力越被稀释，找到关键信息的能力不是缓慢下降而是有明显台阶。
  • 语义匹配难度影响很大：问题与关键信息的语义相似度越低（改写越绕），越难被正确匹配到。
  • 干扰项会反向压制：关键信息与周围干扰内容的相似度越高，被淹没得越严重——这条最反直觉：上下文塞得越"连贯"，表现反而可能越差。

结论：存得下 ≠ 用得上。记忆系统的价值不在于扩容，而在于提高信噪比。

什么时候不该用记忆

  • 一次性、无延续性的任务：比如"把这段 JSON 转成 CSV"。没有"下次"，写入的记忆只会成为噪声。
  • 事实高度不稳定时：如果信息（价格、库存、排期）每天都在变，写进长期记忆反而制造过期污染，应该每次现查。
  • 合规敏感信息：记忆是持久化的，写入前必须考虑数据保留期限与删除机制。以 Claude 的 memory 实现为例，单条 memory 上限约 100 kB（约 25k tokens）、单个 store 上限 2000 条，并且提供不可变的 memory 版本号与内容哈希来支持乐观并发控制，同时支持 redact（脱敏擦除），保留期为 30 天。[来源 7]

常见的失败模式

  • 记忆腐烂：只写不淘汰，旧信息与新事实冲突，模型在矛盾信息里随机选一个。
  • 重复堆积：同一件事被反复写入，检索时挤占名额。这正是整合阶段需要 NO-OP 决策的原因。
  • 幻觉被加固：一次错误的推断被写进记忆，之后每次都被当作事实召回，错误越滚越硬。
  • 摘要失真：压缩与反思都由模型生成，有信息损耗；抽象层次太低会绑死场景，太高又会失去可操作性。

07自测问题

简答题 ① · 概念辨析
Agent 的「记忆」和 RAG 检索的知识库，最本质的区别是什么？请各举一个例子说明。
查看答题要点

要点：区别在于检索对象是否与交互关系本身相关。

  • RAG 检索的是外部静态知识——产品手册、法规条文、公司文档。它与"这次对话是谁在跟我说话"无关。例子：用户问退换货政策，Agent 检索政策文档。
  • 记忆检索的是关于这段关系的信息——用户的偏好、上次做到哪、哪条路走过不通。例子：Agent 记得"这位用户上个月说过他们用 Serverless 环境"，于是这次直接按该前提作答。
  • 补充一句加分点：两者可以同时存在，且往往共用检索基础设施，但写入策略不同——知识库靠人工/离线索引，记忆靠运行时自动提炼。
简答题 ② · 核心机制
Generative Agents 里的记忆检索分数由哪三项构成？各自的含义与计算方式是什么？
查看答题要点

要点：三项加权相加，论文中三个权重 α 均取 1。[来源 2]

  • recency 新鲜度：指数衰减，形式为 0.99^Δt，Δt 以小时为单位。
  • importance 重要性：由 LLM 对记忆打 1–10 分。
  • relevance 相关性：当前查询与该记忆的语义相似度。
  • 加分点：还提到当累积未处理的记忆重要度超过阈值 150 时触发 reflection，把零散观察抽象成更高层结论写回。
简答题 ③ · 核心机制
长期记忆的整合（Consolidation）阶段通常要做哪三种决策？为什么「什么都不做」这一种也需要被显式设计？
查看答题要点

要点：三种决策是 ADD / UPDATE / NO-OP。[来源 8]

  • ADD：全新信息，新增条目。
  • UPDATE：与已有记忆冲突或可补充，改写原条目（处理"过期"）。
  • NO-OP：已有记忆已覆盖，不写。
  • 为什么需要 NO-OP：记忆系统最怕的不是"记不住"，而是重复堆积——同一事实被反复写入，检索时多条同义条目挤占有限的名额，反而降低有效信息的召回密度。显式设计 NO-OP 是在写入端就做去重，属于"防冗余"的成本最低的时机。
简答题 ④ · 风险与边界
为什么上下文窗口变长并不能取代记忆系统？请说出至少两条来自长上下文实测的发现。
查看答题要点

要点：核心结论是"存得下 ≠ 用得上"，因为长上下文下的检索能力会衰减。[来源 12]

  • 非均匀衰减：上下文越长，模型注意力被稀释，定位关键信息的能力出现明显下降，并非缓慢平滑退化。
  • 语义相似度惩罚：问题与关键信息的语义相似度越低（表达越绕、越需要推理），越难被匹配到。
  • 干扰反向效应：关键信息与周围干扰内容的相似度越高，越容易被淹没；反直觉的是，上下文结构越"连贯"，表现反而可能越差。
  • 加分：报告还提到连"重复复制某个单词"这种极简任务，表现也会随长度恶化，说明这是注意力机制的普遍现象而非任务复杂度问题。

选择题 ⑥
关于语义记忆与情景记忆的区别，下列表述正确的是？
  1. 语义记忆存原始对话流水，情景记忆存提炼后的结论
  2. 语义记忆回答"什么是真的"，情景记忆回答"下次该怎么做"
  3. 情景记忆只能用于单一场景，无法泛化到其他场景
  4. 两者只是存储位置不同，用途完全一致
查看答案与理由

正确答案：B。[来源 8]

语义记忆沉淀事实性知识（回答"什么是真的"），情景记忆沉淀带情境的经历（回答"下次该怎么做"）。

  • A 错：描述的是"短期记忆 vs 长期记忆"的差别，不是语义与情景的差别。
  • C 错：恰恰相反，情景记忆中的教训可以跨场景泛化——例如把"某个工具超时"抽象成对某类环境的通用经验，这正是它相对语义记忆的价值所在。
  • D 错：两者用途、写入时机与检索价值都不同。
应用题 ⑦ · 应用场景
假设你要为一个「个人学习助手 Agent」设计记忆系统。请描述：你会写哪几类记忆、分别从哪里来、在什么时机写入，以及你会如何避免它"越记越糟"。
查看答题要点

答题要点（无唯一标准答案，考察是否能落到具体设计）：

  • 语义记忆：用户的知识背景、目标、稳定偏好。来源是对话中明确表达的陈述；写入时机建议由模型判断"这是否是稳定事实"后主动写，避免每句都抓。
  • 情景记忆：某次学习的推进过程与卡点——"上周讲递归时用斐波那契举例没听懂，换成目录树后懂了"。来源是会话过程；建议在会话结束时批量提炼，而非每轮实时写。
  • 反思层：多条情景记忆的抽象——"该用户对抽象定义反应弱，对类比反应强"。触发条件可以是累积到一定数量或重要性阈值，参考 Generative Agents 用阈值触发 reflection 的做法。
  • 防"越记越糟"：①写入端做 NO-OP 去重，同一偏好不重复记；②对时间敏感的信息（正在学的内容、当前进度）标记时效，过期即降权或作废；③保留可撤销能力，允许用户查看并删除记忆，防止一次误判长期污染；④控制条目总量上限，参考工程实践中约 100 kB/条、2000 条/store 的量级设定容量天花板。[来源 7][来源 8]
应用题 ⑧ · 风险与边界
请举出一个"引入记忆反而让 Agent 表现更差"的具体场景，并说明你会怎么修。
查看答题要点

答题要点：

  • 场景举例（幻觉加固）：Agent 在某次对话中把用户提到的"我们好像用的是 MySQL"这一不确定的猜测写进了语义记忆。之后每次技术讨论，Agent 都以 MySQL 为前提作答，用户纠正过两次但旧条目未被更新，导致错误持续。这属于"一次误判被写进记忆，之后每次召回都把它当事实"的典型失败模式。
  • 修法：①写入前做置信度门槛——只有用户明确陈述的事实才写，推测性表述不写；②整合阶段以 UPDATE 覆盖冲突条目，而不是并存；③给条目加来源与时间戳，检索时对旧条目降权（对应 recency 机制）；④提供记忆查看/编辑入口，让人工兜底纠错。
  • 其他可接受的场景：一次性任务被写入记忆成为噪声；记忆腐烂导致模型在矛盾信息间随机选择；摘要失真使关键细节丢失等。
